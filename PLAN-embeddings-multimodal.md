# Plan: Multimodal embeddings input for Junaid.GoogleGemini.Net

**Status:** Implemented and shipped in `6.7.0`. Research live-verified against the real API on
2026-09-11 (design, before any code), then live-verified again the same session after implementation,
through the actual `IEmbeddingService` code, not raw REST calls: image, audio, file-based, PDF, and
mixed-batch input, plus a fresh confirmation (through the typed client this time) that `TaskType` has
zero effect on `gemini-embedding-2`. Full solution build 0 warnings on all three targets; 185/185 unit
tests (13 new); 43/43 non-Batch live tests passing (6 new), no regression to any existing feature.
Video input remains unconfirmed; see §6's update below.

## 1. Goal

`gemini-embedding-2` has accepted image, video, audio, and PDF input since GA (April 2026), mapping
all of them into one shared vector space alongside text. This library's `EmbedContentAsync`/
`BatchEmbedContentAsync` are still text-only (`string`/`string[]` parameters), so a caller cannot
reach that capability today even though the model itself already supports it. This has been a known,
flagged gap in `ROADMAP.md` since the August 2026 audit, and is now the most overdue item on the
backlog: smaller in scope than TTS or STT (it completes an existing feature, not a new API surface),
so it was picked as the next thing to build, with the same rigor: live-verify first, plan, then code.

## 2. What was verified live, and how

Every claim below was confirmed with a real REST call against `gemini-embedding-2`, using real media:
a JPEG generated by this library's own already-shipped image generation, and a WAV generated by its
own already-shipped TTS, the same "use one already-verified feature to test the next one" approach
`PLAN-stt.md` used.

**Confirmed: the existing wire types already support this; only the public method signatures don't.**
`EmbedContentRequest`/`SingleEmbedContentRequest`'s `Content` field is the same `Content`/`Part` type
already used everywhere else in this library (`inlineData`, `fileData`), not a text-only type. The
only reason `EmbedContentAsync(model, text, ...)` can't send an image today is that
`RequestFactory.CreateEmbeddingContent(text)` always builds a text-only `Part`, not that the request
shape can't represent one. This is a smaller lift than either TTS or STT: no new model types, no new
endpoint, no new client method. The gap is entirely in `EmbeddingService`'s public surface.

**Confirmed real request shape**, image input:
```json
POST https://generativelanguage.googleapis.com/v1beta/models/gemini-embedding-2:embedContent
{
  "content": {
    "parts": [
      {"text": "A red circle"},
      {"inlineData": {"mimeType": "image/jpeg", "data": "<base64 jpeg>"}}
    ]
  }
}
```
`HTTP 200`, response shape unchanged (`{"embedding": {"values": [3072 floats]}}`), same
`EmbedContentResponse` type this library already has; no new response type needed.

**Confirmed the image genuinely changes the embedding, not just accepted and ignored.** Compared the
text+image embedding above against a text-only `"A red circle"` embedding: cosine similarity `0.528`
(not `1.0`, not near-zero), and the vectors are not byte-identical. Real multimodal fusion, not a
no-op.

**Confirmed real request shape**, audio input, no text instruction needed:
```json
{"content": {"parts": [{"inlineData": {"mimeType": "audio/wav", "data": "<base64 wav>"}}]}}
```
`HTTP 200`, `3072`-dim embedding.

**Confirmed `fileData` (a Files API URI) works exactly like inline data.** Uploaded the same JPEG via
the existing resumable-upload flow (`IFileService.UploadFileAsync`, unchanged), then embedded it by
URI: `{"fileData": {"mimeType": "image/jpeg", "fileUri": "https://.../files/..."}}`, `HTTP 200`, same
shape. **The Files API integration point is free here too**, same finding as `PLAN-stt.md` §3.2 for
STT: no new upload code needed for large media.

**Confirmed `batchEmbedContents` already accepts multimodal content per-request**, no changes needed
to the batch endpoint itself: sent one plain-text request and one text+image request in the same
batch call, got back 2 separate `3072`-dim embeddings, `HTTP 200`. `BatchEmbedContentAsync`'s existing
one-`Content`-per-request structure already matches the API's "separate embeddings" semantics
(confirmed by Google's docs and this live call); the only fix needed is letting a caller put more than
a text `Part` into each request's `Content`, the same fix as the single-embed case.

**Confirmed a real, undocumented-as-an-error footgun: `taskType` is silently accepted, not rejected,
and has zero effect on `gemini-embedding-2`.** Sent the identical text with and without
`"taskType": "RETRIEVAL_QUERY"`: both `HTTP 200`, and the two response bodies were **byte-for-byte
identical**. Google's docs say `task_type` "cannot be used" for this model and task instructions
should go in the prompt text instead, but the API does not enforce that: it accepts the field, does
nothing with it, and returns 200 either way. A caller passing `EmbeddingOptions.TaskType` with
`gemini-embedding-2` today gets no error and no effect, silently. This is worse than a hard rejection
for DX and needs a prominent warning, not just a docs footnote.

**Confirmed `outputDimensionality` truncation works as documented**: requested `768`, got exactly
`768` values back (vs. `3072` default). No live check of whether Google's claimed
auto-normalization actually renormalizes the truncated vector to unit length; not verified either way
this session.

**Not independently verified this session, same mechanism as confirmed image/audio, high confidence
but not proven:** video and PDF input. Both use the identical `inlineData`/`fileData` request shape
already confirmed working for two different modalities (image, audio) through the same model and
endpoint; there was no quick way to produce real test video/PDF content in this session the way TTS
and image generation provided ready-made real audio/image content. Live-verify both, specifically, in
this library's own live test suite before considering this plan's test coverage complete (see §7).

**Not independently verified: Google's documented per-request limits** (6 images max, 120s video max,
180s audio max, 1 PDF/6 pages max). Not tested against those exact boundaries; taken from docs. The
API's own error message on an oversized request would be the authoritative source if this matters for
a production deployment; this library does not plan to enforce these limits client-side (same
"the API rejects it, we don't pre-validate against a moving target" policy as everywhere else, see §5).

## 3. Explicit scope

**In scope (v1):**
- `EmbedContentAsync` overload(s) accepting inline media bytes (+ optional text) for a single
  embedding.
- An overload accepting a Files API URI (+ optional text) for large media, reusing `IFileService`
  unchanged.
- `BatchEmbedContentAsync` overload accepting multimodal inputs per-request (mirrors the existing
  batch structure; confirmed live it already supports this once each request's `Content` can carry
  more than text).
- A prominent warning (XML doc + `EmbeddingOptions.TaskType`'s own doc comment) that `TaskType` is
  silently ignored on `gemini-embedding-2`, live-confirmed in §2. Consider whether `EmbedContentAsync`
  should log a one-time warning when `TaskType` is set against a model whose name matches
  `gemini-embedding-2`-style naming, mirroring `GeminiCostGovernor`'s existing "warn once per
  unpriced model" pattern, without hardcoding a model allow-list (this library's standing policy,
  see `GeminiConstants.Models`' own doc comment).

**Explicitly out of scope for this change:**
- Generalizing `FileObject` (currently hard-validated as image-only at construction) into a
  general-purpose media type. This is the second feature this session to hit that same rough edge
  (STT hit it too, see `PLAN-stt.md` §2), but redesigning it is a bigger, separate, cross-cutting
  change that would also touch `GenerateWithImageAsync`/`StreamWithImageAsync`/
  `CountTokensWithImageAsync`. This plan follows STT's precedent instead: plain `byte[] data, string
  mimeType` parameters, not `FileObject`. Worth a dedicated pass of its own later; tracked as a new
  backlog item in `ROADMAP.md` once two features have independently needed it.
- Client-side enforcement of Google's documented per-input limits (6 images, 120s video, etc.). Not
  independently confirmed live (see §2), and this library's standing policy is to let the API be the
  source of truth on limits it can change without a library update.
- Video and PDF-specific convenience methods beyond the generic `byte[] data, string mimeType`
  overload. The generic overload covers them (same mechanism, confirmed for two other modalities);
  no modality-specific method is needed the way `TranscribeAsync`/`GenerateAudioAsync` needed to be
  feature-specific methods (those call different endpoints entirely; this is one endpoint for every
  modality).
- `GeminiEmbeddingGenerator` (the `Microsoft.Extensions.AI` `IEmbeddingGenerator<string, Embedding<float>>`
  adapter). Its abstraction is inherently text-input; multimodal embedding input has no natural fit
  there and M.E.AI has no multimodal embedding generator abstraction as of this writing. Leave it
  unchanged; this feature lives on `IEmbeddingService` directly, same as `ITranscriptionService` lives
  outside `IGeminiService`.

## 4. Architecture

### 4.1 `RequestFactory` changes (`Infrastructure/Factories/RequestFactory.cs`)

`CreateEmbeddingContent`/`CreateEmbeddingRequest` currently hardcode a single text `Part`. Add an
overload building a `Content` from an optional text string plus optional inline/file media:

```csharp
public static Content CreateEmbeddingContent(string? text, InlineData? media = null, FileData? fileData = null)
{
    var parts = new List<Part>();
    if (!string.IsNullOrEmpty(text)) parts.Add(new Part { Text = text });
    if (media is not null) parts.Add(new Part { InlineData = media });
    if (fileData is not null) parts.Add(new Part { FileData = fileData });
    return new Content { Role = "user", Parts = parts };
}
```
(Exact signature is an implementation-time call; the point is one `Content` builder reused by both
the single-embed and batch paths, same as today.)

### 4.2 `IEmbeddingService`/`EmbeddingService` new methods

```csharp
Task<EmbedContentResponse> EmbedContentAsync(
    string model, byte[] mediaBytes, string mimeType, string? text = null,
    EmbeddingOptions? options = null, CancellationToken cancellationToken = default);

Task<EmbedContentResponse> EmbedFileAsync(
    string model, string fileUri, string mimeType, string? text = null,
    EmbeddingOptions? options = null, CancellationToken cancellationToken = default);
```
Both validate `mimeType`/media the same way `TranscriptionService` does (`ArgumentException` for
missing/empty input, no attempt to pre-validate mime type against an allow-list). `text` is optional
(confirmed live: audio-only, no text part, still returns a valid embedding).

`BatchEmbedContentAsync` needs a parallel multimodal-capable overload. Candidates to weigh at
implementation time: a new `EmbeddingInput` record (`{Text, MediaBytes, MimeType}`) taken as
`IReadOnlyList<EmbeddingInput>`, or a lower-level overload taking `Content[]` directly for power
users who want multi-part aggregation within one entry (confirmed live in §2: multiple parts in one
`Content` produce one aggregated embedding, a real, intentional feature, not just an accepted quirk).
Lean toward exposing both: a friendly `EmbeddingInput`-based overload for the common case, and keeping
the `Content[]`-based escape hatch available for aggregation, mirroring how `ChatAsync(IList<Content>)`
already sits alongside the simpler `ChatAsync(MessageObject[])` for exactly this "simple path plus
full-control escape hatch" reason.

### 4.3 `EmbeddingOptions.TaskType` doc comment

Add the live-confirmed warning from §2 directly on the property, not just in this plan: silently
accepted and silently ignored on `gemini-embedding-2`, confirmed by an identical-output A/B test, not
merely by reading Google's docs. Cross-reference from `EmbedContentAsync`'s own XML doc too, since
that is the more likely place a caller actually reads before hitting this.

### 4.4 Cost governance / telemetry

No changes expected. Embedding usage already flows through the same `PostAsync`/`UsageMetadata` path
every other `generateContent`-family call uses (embeddings are not Interactions-API-based, unlike
STT); multimodal input tokens should already surface the same way image/audio input tokens do
elsewhere in this library. Live-confirm the `usageMetadata` shape on a multimodal embedding response
specifically before shipping (not captured in this session's research, since the raw REST probes above
did not inspect `usageMetadata`); if per-modality breakdown is present, no plumbing changes needed,
same as STT's finding for `promptTokensDetails`.

## 5. Naming and design decisions worth recording

- **`byte[] mediaBytes, string mimeType`, not `FileObject`.** See §3. Matches STT's precedent
  (`TranscribeAsync(byte[] audioBytes, string mimeType, ...)`), for the same reason: `FileObject` is
  hard-validated as image-only today, and generalizing it is a separate, bigger change.
- **No client-side enforcement of Google's per-input limits.** See §3. Consistent with this library's
  standing "the API is the source of truth on limits it can change without warning" policy already
  applied to model names and voice names.
- **`TaskType` gets a loud warning, not silent pass-through.** The live-confirmed "accepted, ignored,
  no error" behavior (§2) is a real footgun a caller could easily hit without ever finding out their
  task-type tuning had no effect. Worth deciding at implementation time whether this rises to an
  actual runtime warning (logged once, mirroring `GeminiCostGovernor`'s unpriced-model warning) or
  stays doc-only; leaning toward a runtime warning given how silent the real failure mode is.

## 6. Open items (updated post-implementation)

- [x] **PDF input.** Resolved. Live-tested twice: raw REST during the implementation pass (a
      hand-built minimal one-page PDF, `HTTP 200`, `3072`-dim embedding) and again through the actual
      typed client (`MultimodalEmbeddingLiveTests.EmbedContentAsync_Pdf_ReturnsValidEmbedding`).
- [ ] **Video input.** Still open, for an infrastructure reason, not a design doubt. Three different
      public sources for a small real video file (a raw GitHub test asset, a public GCS sample bucket,
      Wikimedia Commons) all failed to connect from this session's sandbox (`HTTP 404`, `HTTP 403`,
      and `HTTP 000`/connection failure respectively), an outbound network restriction in this
      specific environment, not a reachability problem with those sources generally. This library
      also has no video-generation feature of its own to produce test content the way TTS/image
      generation did for audio/image. The mechanism itself (`inlineData`/`fileData` through the same
      endpoint) is identical to the confirmed image and audio paths, so this is a coverage gap, not an
      open design question; live-verify with a real video file in an environment that can reach one,
      before considering this fully closed.
- [ ] `usageMetadata` shape on a multimodal embedding response: still not inspected. Existing
      cost-governance/telemetry plumbing was not touched by this change and is assumed to already
      handle it the same way it handles every other `generateContent`-family response, but that
      assumption was never specifically checked against a multimodal embedding call's real response
      body this session.
- [ ] Whether `outputDimensionality` truncation actually renormalizes to unit length as Google's docs
      claim: still not checked (only the vector length was confirmed, not its norm).
- [ ] The documented per-modality limits (6 images, 120s video, 180s audio, 1 PDF/6 pages): still not
      tested against the real boundary; low priority given §3's decision not to enforce them
      client-side.

## 7. Tests added

**Unit** (`tests/Junaid.GoogleGemini.Net.Tests/EmbeddingTests.cs`), `FakeHttpMessageHandler`-based, 13 tests:
- [x] `EmbedContentAsync(model, bytes, mimeType, text)` sends the correct multi-part `Content` shape
      (text part + inlineData part), and correctly omits the text part when `text` is null.
- [x] `EmbedFileAsync` sends `fileData`, not `data`.
- [x] The batch `EmbeddingInput` overload sends one `Content` per input, each capable of carrying
      non-text parts, and maps each response embedding back to its input in order.
- [x] Validation: missing/empty media, missing file URI/MIME type, an `EmbeddingInput` with neither
      text nor media, an `EmbeddingInput` setting both `MediaBytes` and `FileUri`: all throw
      `ArgumentException` before any network call.
- [x] `EmbeddingOptions.TaskType` combined with `gemini-embedding-2` logs exactly one warning across
      multiple calls (not once per call); combined with an older model (`gemini-embedding-001`) logs
      nothing. Also incidentally the first unit test coverage `EmbeddingService` has ever had at all,
      for any of its methods, text-only ones included; there was none before this change.
